## 1. 作品の輪と、Claude の置き場所

作品の輪は「予想 → 型紙を刷る → 紙で作って試す → 記録と人の説明 → 版の間に Claude が案を出し人が採る → 次の版」。**まず返事をするのは紙**（[philosophy.md](philosophy.md)）。だから Claude は、まず版と版の間の工房に置いた。2026-11-04 に本人は、子どもも AI から直接返事をもらってよいと決めた（[J-013](decisions/J013-core-words.md) の決める点 2 の変更）。作っている途中の手順の質問に、聞かれた時だけ答える口（`src/api/ask.py`、11-04）は作った。仕組みとどの仮説かは答えない。仮説への AI の返事を学ぶ人に直接返す口はまだ作っていない。

| 輪の段 | 誰が | Claude の役 |
|---|---|---|
| 予想を書く | 使い手 | しない。予想が無ければ Claude を呼ばない（床 F9.prediction） |
| 紙が応える | 紙 | しない。紙の返事が先 |
| 記録と説明 | 使い手 | しない。人の説明が先 |
| AI の返事 | Claude | 学ぶ人の記録と説明の後に、直接返してよい。成績にしない（11-04 の決定。口は未実装） |
| 作っている途中 | Claude（聞かれた時だけ） | 切る・折る・貼る・組む順の質問だけに答える。仕組みとどの仮説かは答えない（`src/api/ask.py`。手帖の頁 `src/web/techo_site.py` からも聞ける。本物の API では未実行） |
| 版の間の案 | Claude（工房） | 仮説と寸法の案、記録の解釈の案、次の手の案 |
| 採る | 人 | しない。人が端末で番号を打つまで一覧に入らない |

## 2. 機能の選び分け

道具を 2 つの場所に分けた。**使い手の口**（言葉の仮説を寸法に写す）と、**作り手の工房**（仮説の案を作る）。

| 機能 | どこで | 何をさせるか | なぜこれを選んだか | 選ばなかった物 |
|---|---|---|---|---|
| Messages API（手書きの輪） | 使い手の口、輪の後半 | 言葉を寸法に写す。記録の解釈と次の手の案 | 道具 8 回・やり直し 2 回・1 回 $3 の上限で必ず止め、そこまでを人へ返すため。決定的な床に落ちたら理由を読ませて直させる | Tool Runner（上限と人の確定を自分で握れない） |
| Skill `backstage` | 作り手の工房 | 図と歌と記録から仮説と寸法の案を作る手順 | 工房は作り手が Claude Code で回す。手順を Skill にすれば clone した人の工房でも同じ手順になり、API の鍵が要らない | API だけで回す（作り手にも鍵が要る） |
| MCP サーバ `utsushi` | 作り手の工房 | 寸法の検査、図の拡大、前例、案の全体の検査 | API の輪と同じ決定的な道具を Claude Code から呼ぶ。道具の実装を 2 つ持たない | 道具を Skill の中のコマンドで呼ぶ（API の輪とずれる） |
| サブエージェント `second-eye` | 作り手の工房 | 案の言葉と根拠を、作った者と別の目で読む | 採点の言葉、推測の断定、見分けられない組は機械の床で拾えない。作った者は自分の案の癖に気づきにくい | 同じセッションで読み直す |
| フック（PostToolUse） | 作り手の工房 | 記録や台帳を直した直後に台帳の検査を回し、落ちたら Claude に返す | 根拠の文の照合と要約の一致は、直した直後でないと push の前まで見つからない | push の前だけ検査する |
| モデル | 全部 | 全部 Opus 5.5 | 本人の決定（[J-017](decisions/J017-runtime-model.md)）。**比べて選んだのではない**。選び分けない判断として書く | 段ごとの選び分け（本人が採らなかった） |

**同じ線を 2 つの道で守る。** 工房で Claude Code が作った案も、API が作った案も、同じ受付（`import-draft` と `generate`）に入り、同じ床にかかり、人が採るまで一覧に入らない。どこで作ったかは記録に残る。

## 3. 開発の作り方 — Claude Code のセッションを担当ごとに並べて作る

| いつ | 形 |
|---|---|
| 11-02 から 11-04 の昼まで | 作る側の 1 本のセッションが、調査・設計・実装・検査・記録をすべてした。本人は窓口を通して決めた（[how-it-was-built.md](how-it-was-built.md)） |
| 11-04 から | Issue ごとに担当を分け、担当ごとに worktree を切って、Claude Code のセッションを同時に走らせる形にした。最初の担当の枝、最初の Issue、最初の PR は、どれも 11-04 |

### 役

| 役 | 誰 | している事 |

| 本人 | 人 | 決める。線を引く。作品の考えを言葉にする。実物を見て評価する |

| 統括 | Claude Code のセッション | 本人の言葉を Issue に分けて担当へ渡す。合体の順を決める |
| 担当 | Claude Code のセッション（1 担当に 1 本） | 1 つの線を、自分の枝と worktree で設計・実装・試験・記録し、PR にして合体の道へ出す |
| 別の目 | 作った担当と別のセッション | PR を読み、止めるかを言う。見つけた穴は担当へ返す |
| 受け皿 | 作業環境の側の Claude のセッション | セッションを立てる道具、push の前の検査、合体の道、毎時の自己点検を持つ |

```
本人（手元の iPad のチャット）
  │ 決める・線を引く・実物を見る
  ▼
窓口（本人の個人のエージェント）◀── 判断のキュー（本人にしか決められない事・止めの札）
  │ 本人の言葉を運ぶ                         ▲
  ▼                                          │
統括（Issue に分ける・合体の順を決める）       │
  │ Issue: 目的・ゴールの要件・担当の線・持つファイル・待つ物
  ▼                                          │
担当 1 ─ 枝 1 ─ worktree 1 ─┐                │
担当 2 ─ 枝 2 ─ worktree 2 ─┼─ PR ─ 別の目が読む
担当 3 ─ 枝 3 ─ worktree 3 ─┘         │
                                      ▼
            合体の道（まっさらな clone で 今の main ＋ PR の頭 → ./init.sh → ./run.sh）→ main
```

### 3.1 設計を先に

- **Issue を先に書く**: 書き方は本人の決まり（11-04）で、目的・なぜか・どうしたらいいか（比べた案と推し）・ゴールの要件の 4 つ
- **線を大きく分けた回の設計**: 4 つのループをつなぐ回では、Issue に担当の線ごとの中身・持つファイル・待つ物の表と、合体の順を足した。担当ごとに、持つファイル・読むファイル・待つ物・渡す物・終わりの判定を書き出し、持つファイルが担当どうしで重ならないか、待つ順に輪が無いか、終わりが機械で判定できるかを機械で見てから配った（通らなければ配らない道具）。全部の手間と一番長い待ちの列の比で、並べてどこまで縮むかの上限も出る。この形の記録が残っているのは、この回だけ
- **凍結した基準**: 受け入れの基準を先に固め、変えた時は理由を記録する（`tests/frozen/`）
- **取り込みの関門**（本人の決定 11-04、試行）: 不具合の直し・既存の動作の変更・作り替えは、変える前に落ちて（Red）変えた後に通る（Green）試験を Issue に書くまで取り込まない。試験の判定には出力や測った値の証拠を付ける。合体の後に main で試験を回し、結果を Issue に書き戻してから閉じる（[gate-trial.md](gate-trial.md)）
- **なぜ**: 同時に書くと、同じファイルを 2 つの担当が直してぶつかる。持ち場を先に決めれば、ぶつかる所が書く前に見える。終わりを機械で判定できる形にしておけば、別の目と合体の道が同じ物差しで見られる

### 3.2 担当ごとに worktree を分けて同時に作る

- 1 担当 = 1 つの枝・1 つの git worktree・1 つの Claude Code のセッション。セッションは tmux のセッション 1 つずつに置く
- 枝は今の main から切る。同じ作業の木を 2 つの担当で書かない
- 担当は自分の線の試験を自分の木で回し、PR にする
- **弱さ**: 記録の帳面の末尾に、別々の枝が同時に節を足すとぶつかった。手元の合わせ方では両方を残す指定（`.gitattributes` の `merge=union`）が効くが、GitHub の判定はそれに従わない。節は関連する節のすぐ後に足す、という決まりにした（減ったかは測っていない）。前からある行を直す時は、同じ行を別の枝が直していないかを人が読む

### 3.3 別の目の確かめ（作った者と別のセッションが読む）

- 作った担当と別のセッションが、枝の差分か PR を読む。すべての PR で読んだかは数えていない。作った者は自分の癖に気づきにくい（2 節の `second-eye` と同じ考え）。Claude Code のスキル `code-review`を PR に当てた回もある（[site-requirements.md](site-requirements.md) の 23 節）
- 枝の試験が通っていても、今の main と合わせた木で初めて出る穴がある。たとえば、字を見る試験は通っていたのに、main と合わせると指で触る機器の床の CSS が勝って、話す釦が幅 1100 以下のどの幅でも消えた。これは別の目の見直しで見つけた（[gate-trial.md](gate-trial.md)）
- 止める時は、題に「止め」と PR の番号を書いた札を判断のキューに上げる。合体の道がこの札を見て止める（3.4）
- 見つけた穴は作った担当へ返し、担当が直して、同じ確かめをもう一度通す

### 3.4 合体の道（合わせた木で全部の試験）

- **なぜ作ったか（11-05 20:15）**: GitHub の判定（衝突なし）だけを見て合体した 1 本で、main の試験が落ちた。その PR には別の目の止めの札が出ていたが、見ずに合体した。合体は GitHub の上で起き、手元の push の門を通らない。枝の木は試験していても、合体した後の木は誰も確かめていなかった
- **直した形**: 合体は、どのセッションが打っても同じ 1 つの道を通す。主に見る物は次の順で、どれかで止まれば合体しない
  1. 待っていない: 下書きでない。本文と題に「本人の OK まで合体しません」のような待ちの文が無い。「#N の後に合体」と書いた #N が入り済み
  2. GitHub の判定が、衝突なし
  3. その PR を止める札が開いていない
  4. まっさらな clone で「今の main ＋ PR の頭」を合わせ、`./init.sh` → `./run.sh` の全部の試験が通る
  5. 頭の commit を固定して合体する（確かめた後に枝が動いていたら合体しない）
- **1 本ずつ流す**: 合体の列は鍵で 1 本ずつ流す。main の誤りの直しなど先に通したい物は、統括が書く「先に通す一覧」で前に出す
- push の前の検査（3.7）は、まっさらな clone と `./init.sh` までにした。`./run.sh` の全部はこの道で回す。push の順番待ちを短くするため
- **弱さ**: 列が長くなると、main の誤りの直しを先に通せなかった（先に通す一覧を足した）。11-06 の朝には、列で待つ物が、待っているだけの見張りの命令を「列にいる」と読み違え、並んだ全部がそれに譲って合体が止まった（鍵のファイルを開いている物だけを数える形に直した）

### 3.5 本人の決定の流れ

- 本人は作る側の画面の前にいない。手元の iPad のチャットで窓口に話し、窓口が本人の言葉を統括と担当へ運ぶ（tmux 越しに画面を読み、文を送る）
- 本人の前に出すのは、外に出る操作・文面と哲学の採否・検査に落ちた物の 3 種類だけ（11-04 の本人の線引き）。担当はそれを、全文・選択肢・推し・判断材料を付けた札にして判断のキューに上げる。窓口が 1 件ずつ本人に見せ、答えを本人の言葉で返す
- 3 種類に当たらない小さい判断は、推しで進め、判断・理由・戻し方を 1 件ずつ記録に残す（この repo の外。初めの数件は Issue と同じ 4 つと戻し方の形）
- 11-06 からは本人の委任（「推しで大丈夫そうな時はそっちで推しを選択していいよ」）で、窓口が推しを選ぶ事もある。その時は「本人のタップではない」と印を付けて残す。3 節の形も、窓口が先に委任で選んだ形を、本人が C に差し替えた
- 決まった事は、判断の記録（[decisions/](decisions/)）か、その線の帳面（要件の書き物や[関門の帳面](gate-trial.md)）に残す
- **承認の要る合体**（届け方は 11-06 から）: 利用者に見せる新しい文など、本人の OK を待つ PR は、本文に「本人の OK まで合体しません」と書く（下書きの PR も合体の道が止める）。合体の道はこの文で機械が止める。本人の OK は、窓口が本人の言葉のまま、合体を打つセッションの会話へ届ける。打つセッションは本文の待ちの文を「本人が確かめた」に書き換えてから、いつもの合体の道で流す。承認があっても、合体の道の確かめは 1 つも飛ばさない
- **弱さ**: 窓口の文と本人の言葉の境目は、鉤括弧の引用より外は作る側から見えない。問いの形で届いた言葉を決定と読んで作った事がある（[how-it-was-built.md](how-it-was-built.md) の弱さ 2）

### 3.6 短い文脈で回す（本人の指示で 11-06 から試している）

- 長く動いて文脈が 40 万トークンを超えたセッションは、仕事の節目（PR が入った・手が空いた・引き継ぎの切れ目）で引き継ぎメモを書き、新しく始める。作業の途中では切らない
- メモは 60 行までを目安に短く書く: 担当・今の仕事と次の一手・開いている PR と頭の commit・待っている本人の答え・守る決まりのファイルの場所。会話の中身は写さない
- 新しいセッションは、メモと決まりのファイルだけを読んで始める。大事な決まりは、前から会話でなくファイルに置いている
- 撮影と提出の直前、合体の列の途中、本人の答えを受けて直している途中は切らない
- もとの考えは、長い文脈を持ち続けず、課題と短いメモだけを持って新しく始める、という研究の提案（arXiv 2611.05306）
- **効き目はまだ測っていない**。見方は決めてある: 新しく始めたセッションの文脈の長さ（始めと次の節目）と、別の目に止められた数・やり直しの数を、始める前と比べる

### 3.7 機械で止める所 — push の前の検査と、毎時の自己点検

- **push の前の検査**: GitHub への push は、毎回この検査を通った物だけにした。秘密、公開範囲、生成物、文書の中の存在しないパスなどを見て、まっさらな clone で `./init.sh` が通るかを見る。検査の中身はこの repo には置いていない。止まった回数は提出の日に数え直して書く
- **毎時の自己点検**: セッションを立てる道具の試験と台帳を、LLM を使わずに毎時 1 回点検し、異常の組が前と変わった時だけ判断のキューに上げる。提出の日の正午に止める
- **記録の台帳**: 決定・調査・判断待ち・主張と根拠を JSON に持ち、表は描画する。根拠の文が今もファイルにあるかを試験が見る
- 合体の道・push の前の検査・自己点検の道具は、この repo の外にあり、提出物に含めない（README の「開発基盤と提出物の切り分け」）

#### Claude の機能と、選んだ理由（作り方の側）

| 使った物 | 何に | なぜそれを選んだか |
|---|---|---|
| Claude Code のセッション（担当ごとに 1 本） | 1 つの線の設計・実装・試験・記録 | 線ごとに文脈を分ければ、互いに待たない線を同時に進められるため |
| git worktree | 担当ごとの作業の木 | 1 つの repo を、担当ごとに別の木で同時に書くため。1 つの木を 2 つの担当で書くと、互いの途中の変更が混ざる |
| tmux | セッションを 1 つずつ保ち、窓口と統括が画面を読んで文を送る | 本人がその場にいなくても止まらずに動き、外から運転できるため |
| 判断のキュー | 本人にしか決められない事と止めの札を、1 か所に並べる | 画面ごとに流れた問いが消えないため。合体の道も同じ札を見る |
| Claude Code のスキル `code-review` | 別の目の確かめの 1 つ | 作った者の文脈の外から差分を読むため |
| 引き継ぎメモと決まりのファイル | 新しく始めたセッションが続きを持つ | 長い文脈を持ち続けないため。決まりが会話に埋もれないため |

#### 作り方の弱さ

- 合体の道ができる前は、GitHub の判定だけで合体して main の試験を落とした（3.4）
- 合体の列が長くなり、直しを先に通せなかった。待っているだけの命令を読み違えて、合体が止まった（3.4）
- 枝どうしの末尾の追記がぶつかった（3.2）
- 判断待ちで止まった時間（最長 124 分）は、1 本の時期の 11-02 の午後から夜（14:00〜20:33）に測った。中継の取り違えも 1 本の時期の物（[how-it-was-built.md](how-it-was-built.md) の弱さ 1・2）。並べた後の待ちの時間は、まだ測っていない

#### 物語の一文
