# 14 審査基準の 4 項目に照らして点検する

**一次資料**: キックオフの審査基準の振り返り（主催の Discord の再掲を本人経由で受け取った）。書き手は Discord の原文を見ておらず、下の文は届いた文面のまま。配点は開始前のメモで見た参加者ガイドの配点と同じ。

**事前メモとの関係**: 問題設定の「後継者不足」は事前の本人の口述のメモにある。比較はここで初めて行った。

**採点は書き手（Claude Code のセッション）の見立てで、測定ではない。** 点検した時点は 2026-11-02 21 時台で、提出は 11-08 20:00。

## 基準（届いた文面）

- **インパクト 30%**: 課題が本人の現場から出発しているか／誰が・どんな場面で・どれくらい困っているかが具体的に描けるか／ハッカソン後も誰が使い続けるか言えるか。
- **デモ 25%**: 冒頭で「誰の・どんな課題を・どう解決するか」が明確か／前提知識なしで操作の流れから価値が分かるか／最後まで見たくなるか。
- **Claude の活用 25%**: 基本を超えた新しい使い方／Claude Code を中心に据えて何が可能になったか／モデルや機能（Skills・サブエージェント・MCP・フック）の選び分け。
- **深さと実行力 20%**: 試行錯誤で磨いた跡／設計と実装の丁寧さ／困っている人がそのまま使える仕上がりか。

## 弱い所 1: インパクトの具体像と継続利用

問題の言い方が 2 つあり、1 つに決まっていない。

| | A 後継者不足 | B 知識伝達型の教育への挑戦 |
|---|---|---|
| 出所 | 事前の本人の口述（触れる機会がない → 触れていない → 興味が湧かない） | 本人の言葉（[J-013](../decisions/J013-core-words.md)） |
| 強い所 | 社会の課題として分かりやすい | 今の設計の核と一致する |
| 弱い所 | 紙工作が担い手を増やすかは測れない。型紙の先が職人につながっていない | 「誰がどれくらい困っているか」を言いにくい |

**追記**: この点検の後に本人の言葉が届き、問題の言い方が C として定まった。「手元のトイモデルで自然とやりとりする体験が足りない。無いと、大型の装置や計算資源を使う科学にしか真理がないと思ってしまう」（[philosophy.md](../philosophy.md)）。B と矛盾せず、A より今の設計に近いので、C を主にする。主語の注意は [research/15](15-philosophy-review.md)。

「足りない物」はこれで言える。残りは現場の具体で、**本人が誰を見て、どの場面でこの問題を感じたかは、書き手には分からない。作らずに本人に聞く。** 架空の利用者を書くと、審査の問いに答えたように見えて、一番大事な所が嘘になる。

継続利用も同じで、名前を挙げられる使い手が今はいない。候補は本人自身（残りの図を試し続ける）、教員や親、玩具の店や博物館の工作の会。どれも当てがあるかは確かめていない。

## 弱い所 2: デモの冒頭

今の要約を読んで分かるのは「何か」で、「誰の課題か」は分からない。冒頭の文は上の答えが決まらないと書けない。形だけを先に決める。

> （誰）は（どんな場面）で（どう困っている）。この作品は（どう解く）。

本人の言葉で埋まる所まで埋めた下書き（括弧は本人の答え待ち）:

> （誰）は（どんな場面）で、科学の面白さは大きな装置の向こうにあると思ってしまう。この作品は、江戸の玩具を紙と糸で作り、予想に紙が応える体験を手元に渡す。

流れの見せ方は、絵を見る → 予想を書く → 紙を刷る → 作る → **紙が開く、または開かない** → 考えが変わる → 次の版、を操作の説明なしで見せる。必要な物は、実物の試行の映像と、コマンドでない入口。

## 弱い所 3: Claude の機能の選び分け

事実を先に並べる。

| 機能 | 今 | 選んだ理由、または無い理由 |
|---|---|---|
| Claude Code | 開発の全部 | 調査、実装、検査、記録を 1 本で通すため |
| サブエージェント | 3 回。持ち寄りの検品、前提の批判、AI の読み手の試験 | 作った者と別の目が要る所だけ |
| Skills | 開発中に公式の `claude-api` を参照しただけ。この repo の Skill は無い | 作っていない |
| フック | Claude Code のフックは repo に無い。push のゲートは git のフックで、repo の外 | 作っていない |
| MCP | 使っていない。絵の拡大と寸法の検査は Messages API の道具（`src/api/tools.py`） | 比べていない |
| モデルの選び分け | 製品の API は全部 Opus 5.5（`src/api/config.py`）で、未実行 | 本人の決定（[J-017](../decisions/J017-runtime-model.md)）。追記: この点検の後に決まった。選び分けない判断で、比べた結果ではない |
| Messages API の手書きの輪 | 作った。偽の応答で試験しただけ | 上限と人の確定を自分で握るため（[J-010](../decisions/J010-loop-back-half.md)） |

つまり、**語れる物語はまだ無い。** 無い物を語らず、作るなら理由のある物だけを作る。案は次のとおり。

| 案 | 中身 | 良い所 | 弱い所 |
|---|---|---|---|
| a | 今の手書きの輪のまま、本物の API を回す | 追加が少ない。設定と鍵だけ | 機能の選び分けの物語は増えない |
| **b（推し）** | 裏の制作を Claude Code の上に組む。Skill（型紙を作る手順）、サブエージェント（別の目）、フック（`ledger` と検査を毎回通す）、MCP（寸法の検査と絵の拡大を Claude Code から呼ぶ）。言葉の口だけ API | 使い手の口と作り手の工房で道具が分かれる理由を語れる。clone すれば同じ工房が動く。作り手は API の鍵が要らない | 作り直しの手間。本物で回すまで効くか分からない |
| c | Managed Agents に移す | 走らせる面倒が減る | 週内に移す理由が今は無い。比べていない |

b でも、Skills などの有無が加点になるとは書かれていない。基準の文は「選び分け」なので、数を揃えても点にはならないと読む。
