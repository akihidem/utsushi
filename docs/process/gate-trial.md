- **関門**:
  1. 検証ゲート: 不具合の修正・既存の動作の変更・作り替えは、Red（変更前に落ちる）→ Green（変更後に通る）の検証を issue に書くまで、取り込みに進めない
  2. エビデンスゲート: 試験の判定には証拠（出力・成果物・測った値）を付ける。付けられない時は例外を宣言し、代わりの証拠を付ける。「動いた」だけでは通らない
  3. マージ後の書き戻し: 取り込んだ後に試験を回し、結果を issue に書き戻してから閉じる。書き戻しが無ければ issue は開いたまま
- **issue の書き方**（同じ日の本人の決まり）: 目的・なぜか・どうしたらいいか（代替案と推し）・ゴールの要件
- **この帳面の使い方**: 1 件 1 節。各関門の「済み・まだ・当たらない」と証拠の場所を書く。窓口が動きを見られるよう、かかった手間と気づきも書く
- **証拠のファイル**（#171）: `python -m omochae.gate_evidence write <名前> -- <命令>` で書く。頭に命令と commit が入り、手元のパスが除かれる。`python -m omochae.gate_evidence check` で頭の無い物を名指しする。#171 より前の証拠で命令が残っていない物は「残っていない」と書いてある（推測で埋めない）
- **合わせ方**: 枝どうしの末尾の追記は、手元の merge なら `.gitattributes` の `merge=union` で両方が残る。GitHub の判定は従わないので、節は関連する節のすぐ後に足すとぶつかりにくい（#232）。前からの行を直す時は、同じ行を別の枝が直していないかを人が読む
