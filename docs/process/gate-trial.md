- なぜか: 日割りの表（`src/api/budget.py` の DAILY_CAP）は期間の 7 日だけを持ち、表に無い日は上限 0 と読んでいた。提出の翌日から、手順の質問・Claude の読み・動画の観察・仮説の生成が、1 回目の呼び出しの前に全部止まる。審査で repo を動かす人にも、提出の後に使い続ける本人にも当たる。画面の文は「予算の上限」だけで、日付が原因だと分からなかった
- どうしたらいいか: 推し（#150 の推し。本人の決定、11-05）は、表に無い日を既定の日割りで続ける事。額は「今の表の日割りと同じ額」で、表は日ごとに額が違うので、表の最後の日の $50 を先の日にも使う読みにした。額は DEFAULT_DAILY_CAP の 1 か所。代案 A: 表を先の日付まで延ばす（同じ形でまた切れる）。代案 B: 表に無い日は累計の停止線だけで止める（1 日で使い切れる）
- 足した決め: 止めた線を BudgetStop に持たせ、画面の 3 つの口（玩具の頁の手順の質問・手帖の手順の質問・手帖の Claude の返事）が同じ短い文で言う。待てば聞けるのか（今日の上限）、待っても聞けないのか（累計の停止線）が分かるようにする。額と作る側の言葉は画面に出さない。玩具の頁の口は、額の入った例外の文をそのまま出していた
- 出していない範囲: 台帳がデモと本番で別々になる件（#151）。上限の値そのものは変えていない（表の 7 日の額と累計の停止線 $475 はそのまま）
- ゴールの要件: 表に無い日でも、既定の上限の中なら check が通る。表にある日の額と累計の停止線は変わらない。止まった時の文が今日の上限か累計の停止線かを言う。期間の後の決め方が文書にある。必須 2 種の紙の指紋が変わらない。`./run.sh` が rc 0
- 検証ゲート: **済み**。Red: rc 1、BudgetStop「日割りの上限 $0 に達する」（直す前の main 6da8073。gate-evidence/red-budget-after-period.txt）。Green: rc 0「ok」（gate-evidence/green-budget-after-period.txt）。試験を空振りさせないよう、直した木を 7 通りに書き換えて、どれも落ちる事を見た
- エビデンスゲート: 上の出力と、直した作業ツリーでの `./run.sh`。`tests/test_floor_pin.py` も通る（型紙と手順の紙は変えていない）。本物の API は呼んでいない（試験は、呼ぶ前の見張りだけを通す）
- 確かめ待ち: 既定の額の読み（$50）。別の額が届いたら、DEFAULT_DAILY_CAP の 1 行だけを変える
- マージ後の書き戻し: Issue #150 に書く（この帳面へは、次に帳面を書く取り込みで写す）

## 道具が足りない機械で、落ちる（3）でなく検査できない（4）にする（Issue 対応の担当、issue/160-missing-tool-rc4、11-05 朝。#160）

- 目的: まっさらな機械で README のとおりに進めた人が、足りない道具を名前で知らされる
- なぜか: `tests/test_demo_assemble.py` と `tests/test_ai_feedback.py` は ffmpeg を直に呼ぶのに、README・`init.sh`・床の入口の一覧に ffmpeg が無かった。無い機械では `./run.sh` が rc 3 になり、不足が「落ちた」に見える。`.venv` が無い時に床の入口を直に呼ぶと、トレースバックの rc 1 になる
- どうしたらいいか: 推し（#160 の推し）は、床の入口と `init.sh` の確かめに `ffmpeg`・`ffprobe` を足し、無ければ名前を言って 4。README にも書く。代案は、ffmpeg の要る試験だけ飛ばす形。全体が 4 にならない分、見落としやすいので採らない
- 推しに足した物: 床の入口で `.venv` と字も見る（字が無い時も同じ形で 3 になり得るので、一覧をそろえた）。足りない物は 1 回で全部言う。uv は環境を作る時だけ使うので、床の入口では `.venv` を見る
- 出していない範囲: デモ動画の書き出しに要る Chrome か Chromium。`./run.sh` では使わないので #168 で扱う
- ゴールの要件: ffmpeg を PATH から外して `./run.sh` が「ffmpeg が無い」で rc 4。`.venv` が無い時に `python tests/run_floors.py` が rc 4。README・`init.sh`・`tests/run_floors.py` の一覧が同じ

## 記録の読み書きを壊れにくくする（Issue 対応の担当、issue/153-records-robust、11-05 朝。#153）

- 目的: 記録のファイルが 1 つ壊れても、ほかの頁は開く。書きかけのファイルを作らない。同時に押しても記録を取り合わない
- なぜか: 書きかけの記録が 1 つあると、玩具の頁・手帖・ギャラリーが全部 500 になり、ログにもどのファイルかが出なかった。デモは 3 台が同じ置き場に書き、#109 を入れるとサーバが 2 つのプロセスに分かれる
- どうしたらいいか: 推し（#153 の推し）の 3 つを 1 組で入れた。書き込みは `src/omochae/store.py` の 1 つの関数へ寄せ、読めない物は飛ばしてファイル名を stderr に出し、番号取りと読んで足して書く所は置き場の `.lock` を flock で取る。比べた代案のうち、サーバを 1 スレッドにする形は、遅い要求 1 つで全部が待つので採らない。`threading.Lock` はプロセスをまたげないので採らない
- 足した決め: 必ず要る 1 件（採る提案・足し込む先の台帳）は飛ばさず、ファイル名を言って止める。飛ばすと壊れた台帳を新しい中身で上書きするため
- 出していない範囲: 持ち寄りの置き場の読みは前から飛ばす形なので触っていない。予算の台帳（`src/api/budget.py`）も触っていない（#151）
- ゴールの要件: 書きかけの記録が 1 つあっても頁が 200 で開き、ファイル名が記録に出る。同時に 2 本の次の版を送っても提案と版の番号が重ならない。記録・輪・予想の書き込みが全部、一時ファイル → 置き換え を通る
- 検証ゲート: **済み**。Red: 直す前の main に試験を当てて 14 件中 13 件が落ちた。番号は `G-0001` が 6 本、版 2 が 2 本で重なった（gate-evidence/red-records-robust.txt）。Green: 14 件全部が通る（gate-evidence/green-records-robust.txt）。同時の試験は読んだ直後に待ちを入れ、運に任せない
- エビデンスゲート: 上の出力と、直した作業ツリーでの `./run.sh`。`tests/test_floor_pin.py` も通る（型紙と手順の紙は変えていない）。プロセスをまたぐ試験は実際に子のプロセスを 3 つ起こす。実機の 3 台では確かめていない
- 所見: 採る処理は全体を排他に入れたので、中の検査（型紙を組む）の間は、同じ置き場の書き込みが待つ。1 秒ほどの見込みで、測ってはいない
- マージ後の書き戻し: Issue #153 に書く（この帳面へは、次に帳面を書く取り込みで写す）
