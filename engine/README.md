# paper-to-toy — 紙で試すための型紙（papercraft）のエンジン

Paper to toy は、内部構造のある機構を、紙のような2次元素材を中心とした原材料で作る設計ができるエンジン。

型紙（papercraft）を作るエンジン。江戸の玩具を紙で試すために、寸法から型紙の PDF を作り、刷れる・組めるかを機械で検査する。**Built with Claude: Japan 2026（ハッカソン）で作っている。**

A papercraft template engine: generates printable PDF patterns from dimensions and checks them before and after rendering. Being built at Built with Claude: Japan 2026 (hackathon).

## 地平

制作者の言葉（2026-11-07）:

- 「内部構造を持つ機構をつくれるシステム」（paper-to-toy の核の言い方）
- 「これを基礎で支えるのが paper to toy で、物理現象とか DNA とかなんでも紙で作れるモデルを生成できるようにするのはどう？」

江戸の玩具は最初の題材です。寸法から刷る部品を出す雛形・刷れるか組めるか動くかの検査・3D で折って組む確かめ・作った人の報告で直す輪は、題材を選びません。物理現象や DNA の二重らせんのような、内部構造を持つ機構の紙のモデルは、江戸の玩具とは別の題材ですが、江戸の玩具から外へ広げた物ではなく、paper to toy の原点にある考えです（上の制作者の言葉）。その 2 つ（振り子の波と DNA の二重らせん）を、試作して開発中です（下の「エンジンの原点にある模型（試作して開発中）」）。ほかの模型へ広げる事を、地平として置きます。

## 何をするか

型紙は正解ではなく、AI が考えた仮説です（どの紙にもそう刷る）。作って、動きを確かめて、直していきます。作り方を決めた制作者の言葉は [docs/philosophy.md](docs/philosophy.md) にそのまま残しています。

制作者 = この repo の作り方を決めた人／作った人 = 型紙で玩具を作った人


```
寸法（JSON） → 配置 → 描く前の検査 → SVG / PDF → 刷った後の検査 → PNG
```

- **描く前の検査**: 寸法の範囲、部品と文字が印字域に収まるか、部品どうし・文字どうしの重なり（文字の幅はフォントから測る）、部品表の素材と刷る部品が全部載っているか、描き直しの絵が折り線と糊代をまたがないか、穴が部品の中にあるか、雛形ごとの物理（扇が筒に収まるか・押し切れるか・像の足が台に貼れるか・重心が軸より下か など）。
- **刷った後の検査**: できた PDF から pdftotext で、所蔵の文・永続 ID・改変の注記・出典 ID・仮説の文が、そのまま読み直せるか。貼られた画像が 0 枚か（原図を貼らず描き直す）。
- 検査に落ちた紙は正しい名前で残さない（刷った後の検査で落ちた紙は `*.rejected.pdf` だけにし、描く前の検査で落ちた時は同じ名前の前の回の紙も消す）。検査できない（exit 4）時は、前の回の紙に触らない。

雛形は、提出物（utsushi）と同じ 2 つと、『江都二色』のほかの玩具の雛形（下の 2 つ目の表）と、エンジンの原点にある模型の試作 2 つ（振り子の波・DNA の二重らせん。その下の節）。

| 雛形 | 玩具 | 仕組み | 刷る形の寸法（必ず書く） |
|---|---|---|---|
| `slider_fan` | 御来迎 | 角筒の中で動く台に蛇腹の扇と像を載せ、押し上げると開く。扇の中心の置き方も描き分ける（`hub`: `axle` 軸・`rim` 口の台。既定 `axle`） | `push_part`: `tab` つまみ・`tube` 内筒・`stick` 棒 |

### エンジンの原点にある模型（試作して開発中）

制作者の言葉（2026-11-07）「作ってみる。試作して開発中と書く」。物理現象や DNA のような、内部構造を持つ機構の紙の模型は、江戸の玩具とは別の題材だが、江戸の玩具から外へ広げた物ではなく、エンジンの原点にある物（制作者の言葉（同じ日）「原点にあるやつ」・上の地平の節）。その試作が次の 2 つ（始めの指示は同じ日の「何個かつくってみてよ。」）。どちらも刷る所までできていて、描く前と刷った後の検査を通る。まだ紙で組んで確かめていない。3D の組み立て検品もまだ（3D で組んで確かめているのは御来迎と首振り虎だけ）。

| 雛形 | 模型 | 仕組み | 刷る形の寸法（必ず書く） |
|---|---|---|---|
| `pendulum_wave` | 振り子の波（物理の作例） | 長さを少しずつ変えた振り子を梁に V の字で吊る。Γ 秒に、いちばん長い振り子が n0 回・次が n0 + 1 回…振れる長さにするので、放すと波のように見え、Γ 秒でまた全部がそろう | `kind`: `wave` |
| `helix` | DNA の二重らせん（B 形・右巻き） | 塩基対の V の字の板を竹串に通し、間の筒で 1 段の高さをそろえて積む。2 本の背骨の帯を、印の間の長さ（らせんの上の隣の塩基対の間）のとおりに腕の先へ貼ると、1 段に 360°/10.5 ≈ 34.3° のねじれが決まる。2 本は逆向き（5'→3'）、腕の間 140° で小さい溝と大きい溝が交互に見える | `kind`: `bdna` |

刷る（既定の寸法。振り子の波は 6 本で 20 秒、DNA の模型は 11 段）:

```bash
PYTHONPATH=src .venv/bin/python -m omochae --scenario examples/pendulum_wave.json --out out/pendulum_wave
PYTHONPATH=src .venv/bin/python -m omochae --scenario examples/helix.json --out out/helix
```

- 出典の印: 所蔵の代わりに、出典の記録の `reference`（文献か原理の文）を「出典: …」と刷る。`omochae.marks` は `reference` を持つ出典ではその文を刷り、刷った後の検査もその文を探す（古い刷り物から起こした型紙の印と見方は前のまま）。振り子の波は物理の原理の文（小さな振れの振り子の周期の式 T = 2π√(L/g)。長さはこの式で出す。糸は玉の真ん中を揺れの軸と平行に通るので、玉は糸を軸に回れて、玉の回る重さは入れない）。DNA の模型は文献（Watson と Crick 1953。1 回り 10.5 塩基対は、測った値 10.4（Wang 1979）と 10.6（Rhodes と Klug 1980）の間）。
- 振り子の長さは 59〜77mm（A4 に刷れる塔の高さに収まる長さ）。20 秒の間に揺れが残って波が見えるかは、紙で組んで確かめる。
- DNA の模型の 2 本の腕の間の 140° は、溝を見せるための見込みで、原子の位置から測った値ではない。原子の形や、らせんがほどける動きは表していない。

玩具 1 つに型紙は 1 枚（制作者の決定 2026-11-05「型紙は説を羅列せず、おもちゃ一個につき一個にする」）。同じ玩具で動き方の読みだけが違う形（`slider_fan` の `tab`・`tube`・`stick`・`lift`（御来迎の型紙は `rise`。制作者の決定 2026-11-06）、`pivot_counterweight` の `hang`、`slide_box` の `sleeve`、`popup_jar` の `hex`、`float` の `cups`）は型紙にせず、試行錯誤のヒントとして残す。どれが型紙かは `omochae.sheets` の表にあり、`omochae.ways --json` の `sheet`・`reading_of` に出る。型紙の 1 枚も答えではなく、たたき台。

寸法を直に渡す入口（`--template` と `--params`）では、刷る形の寸法を既定の値に頼らず必ず書く（どの形を刷ったかを、呼んだ側の JSON に残すため）。

どの寸法も計算と検査で出した値です。検査は「刷れる・形の上で組める」事を見る物で、紙で動く事の保証や、昔の作り方の証明ではありません。

## 使い方

Python のパッケージ名は `omochae`（元の repo と同じ名前のまま）。

要る物: Python 3.11 以上、[uv](https://docs.astral.sh/uv/)、poppler-utils（`pdftotext`・`pdfimages`・`pdftoppm`）、fontconfig（`fc-match`・`fc-list`）、字 Noto Serif CJK JP。

Ubuntu 24.04 では、まっさらな環境からこれで揃う（Docker の `ubuntu:24.04` で確かめた）:

```bash
sudo apt-get update
sudo apt-get install -y python3 pipx poppler-utils fontconfig fonts-noto-cjk
pipx install uv   # uv の入れ方は https://docs.astral.sh/uv/ の物でもよい
export PATH="$HOME/.local/bin:$PATH"   # pipx が uv を置く所
```


```bash
./init.sh     # .venv を作り、依存を入れる。足りない物があれば名指しして exit 4
./run.sh      # 凍結した場面と試験を全部回す。結果は out/RESULT.md
```

最小の例（型紙を 1 枚刷る）:

```bash
PYTHONPATH=src .venv/bin/python -m omochae --scenario examples/fan_tab.json --out out/fan_tab
# → out/fan_tab.svg / .pdf / .png
```

`examples/fan_tab.json`:

```json
{
  "template": "slider_fan",
  "source_id": "NDL-1187053-R0000005-L",
  "params": {"push_part": "tab"},
  "inject": {}
}
```

型紙の題に刷る版の番号（`版 N`）は、`--version` か、場面の `version`（型紙の版。見本の虎 `examples/tora_v7.json` は 7、御来迎 `examples/goraigo_v14.json` は 14）。どちらも無ければ 1（1 以上の整数でない時は 4）。場面の `title` は題の全体を置き換えるので、その時は版も `title` に書く。撮影中の虎 v6 の見本は番号を持たない（刷った紙の題は「版 1」のまま）。決める側の決定（2026-11-07）「紙の題の版も見本に番号を持たせる形で」による。前は見本から版を渡さず、どの版の紙も「版 1」だった。型紙の版は、エンジンの版（`data/engine/versions.json`。どの型紙の版をどのエンジンの版で刷ったか）と別の番号（試験 `tests/test_sheet_version.py`）。

寸法の JSON を直に渡す時は `--params`（`--template` で雛形を選ぶ。出典は雛形ごとに既定がある）:

```bash
echo '{"mount": "hang", "axle_height": 50}' > tiger.json
PYTHONPATH=src .venv/bin/python -m omochae --template pivot_counterweight --params tiger.json --out out/tiger
```

引数の説明は `PYTHONPATH=src .venv/bin/python -m omochae --help`。

`params` に書かなかった寸法は雛形の既定値（`DEFAULTS`）を使う。変えてよい名前と範囲は雛形の `RANGES`。`source_id` は `data/sources/` の出典の記録の名前で、型紙に刷る所蔵と改変の印をここから取る。

描かずに検査だけを回す時は Python から（`PYTHONPATH=src .venv/bin/python` で）:

```python
from omochae.compose import check_params
import json
source = json.load(open("data/sources/NDL-1187053-R0000005-L.json", encoding="utf-8"))
print(check_params("slider_fan", {"push_part": "tab", "fold_count": 40}, source))
# {'passed': False, 'errors': [
#     'FAIL F5.fan_clearance [蛇腹の扇] 帯の長さでは 406° 開くが、筒の口の角に当たって 289° までしか開けない',
#     'FAIL F5.print_area [蛇腹の扇] 印字域の外に出ている (127.0, 36.2, 200.0, 376.2)',
#     'FAIL F5.text_overlap [糊代] 文字が部品「蛇腹の扇」と重なっている',
# ]}
```

## 分かっている事

- つまみで動かす形（`push_part: tab`）は、溝を筒の下の端まで開いた切り込みにしてある（くり抜くより切りやすいため）。溝の下に止めが無いので、内筒は手で支えて押す。紙の摩擦で止まるかは実物で確かめていない。
- 御来迎の次の版の形（`push_part: lift`、2026-11-06 の制作者のレビューから採った案）: 扇は糸を一切使わず、2 受け（U の字。底と左右の面が糊代）で扇の下の端と両端の板を束ね、蛇腹の折り目のばねで開いておく。1 外筒をかぶせると扇は畳まれ、筒を上へ外すと開く。内筒・竹串・糸・穴は無く、扇の足も無い。台は印のある上の面を上にして糊代を下へ折る（山折り）。紙で開くか・筒の中で畳まれるかは、実物で確かめていない。床は、筒がかぶさる事（F5.fan_height・F5.figure_height）・受けと扇が台と筒に収まる事（F5.base_size・F5.fan_thickness）だけを見る。3D の確かめ（fold3d）は、つまみの形だけを組むので、この形は確かめられない（4）。制作者の決定（2026-11-06「筒を外す形（lift）はやめる。下から押し上げるバージョンを作る。側面のつまみのバージョンは廃止。内筒を付ける。」）で、この形はやめ、試行錯誤のヒント（別の読み）として残す。今の組の形（tab・tube・stick）は変えていない。

  - 既定の寸法は上限に近い（紙の厚さで約 3.7%、引きで約 5.6% 増えると越える）。紙の厚さは、刷った止めの条件（重りを下げた時の下がり）で確かめる。条件を満たさない腕は使わない。
  - 引き金の掛け方と外し方、弩の腕の根元の折りの硬さは確かめていない。
  - おはじきやビー玉など硬い物は、形では筒に入るのを止められない。止めているのは組み方の文だけ。
  - 引き金の細い切れ込み（幅 2mm）は外形の一部なので、組み方の文は「部品を実線で切る」に含めている。大人が切るとも、カッターとも言っていない。
  - 弓と毛玉（`form: bow`）は、放すと毛玉が前へ動くが、弓の真ん中の持つ所と握る手に当たる見込み（作って確かめていない）。弦は張らずに結ぶので、休む時の弦は弓の帯の上にあり、毛玉の通り道の正面に持つ所の帯がある。既定の寸法では、黒い線まで引いた時の毛玉の前の面から持つ所までが 6mm で、弦は弓の線から 9〜12.8mm の所まで張っているので、毛玉は弦に押されたまま当たる。型紙には残し、刷る紙の「用意する物」の終わりに断りを 1 行書く（2026-11-06 の制作者の決定）。断りの 1 行の分、弓の紙の下の端が 3.75mm 下がるので、印字域の下の端まで余りの少ない寸法の組（紙 40g/m² で玉の紙 90mm など）は、印字域に収まらず F5.print_area で落ちる。
  - 弓と毛玉の出典の図（コマ 29 左）に、弦は描かれていない（少し反った細い棒の先の近くに糸を結び、糸の先に毛玉が付いている）。棒を弓と読み、弦を結んで毛玉を飛ばす形にしたのは、この雛形の解釈。
- `stand_figure`:
  - 立つかは、姿の面の重心が足の形（脚なら姿の下の縁と脚の先、台なら箱の底）の内に、重心の高さ × tan 8°（2mm 以上）の余白を持って入るかで見る。脚の帯の重さは重心の奥行きに入れ、台の重さは入れない。どの姿も実物で立てていない。
  - 脚は 1 本の帯を三角に折って閉じた物（背に貼る面・脚・つなぎ）で、貼る面を姿の背に貼る。姿は後ろへ 20° 傾けて立て（開きの角の既定は 40°）、開きは三角の辺の長さで決まる。折り目 3 本と閉じる位置が 0.5mm ずつ、貼る高さが 1mm ずれた組み合わせ全部で、前へも後ろへも倒れない事を見る。ずれの大きさは見込みの値で、帯のたわみと紙の厚みは入れていない。
  - 脚の帯と台の箱は、色の面を外にして山折りする（凡例の谷折りは刷った面がへこむ向き。山折りにすると糊代の斜線が貼る相手を向く）。表と裏の姿は、粗く切って貼り合わせてから、実線で 2 枚いっしょに切る。
  - 台の溝（幅 1mm）は 2 本の線の間の帯をカッターで切り取る（大人がする）。舌は箱の高さより 1.5mm 長く、上の面と底の 2 つの溝を抜けて机に着く（姿の下の縁は上の面から浮く）。溝の隙間で 5° まで傾くと見るが、手で切る溝の幅のずれ（±0.4mm）と箱の折りのずれ（±0.5mm）は見込みの値。舌は 1 つの足の下に差し（2 本の脚にまたがる溝は落とす）、横は舌の幅だけで支えると見る。
  - 姿の輪郭と絵は図を見て手で取った点で、細い棒（面の柄・首の竿）は紙で切れるよう図より太くした。
  - 立て方と脚・台の寸法の既定は姿ごとの勧めで、`--params` に書いた値が勝つ（姿ごとの既定は `spec()` の `figures`）。`scale`（0.75〜1.5 倍）を変えると、脚の長さ・貼る面・溝の長さの勧めも同じ倍率になり（溝は舌の検査が通る範囲に収める）、脚の幅は小さくする時だけ縮み、台の奥行きは大きくする時だけ広がる。1 倍より大きい姿は A4 に入らない物が多い（`--page B4`）。
  - どの姿も勧めのままで通る倍率は 0.88〜1.3 倍（1 倍より大きいと B4）。首人形の 0.87 倍以下と細い鳥の竿の 0.75 倍は、足が細いか足の間が狭く、溝をどう書いても通らない。1.3 倍より大きいと B4 にも入らない姿が増え、羽子板は 1.49 倍から台の横が足りない。手のずれの見込みは倍率で変わらず、脚の帯の座屈も見ていないので、1 倍から離れるほど実物で確かめる要がある。
- 作った人の報告の個人の情報の検査（F12.pii）は補助。次は式では落とせず、受け入れる前に人が全文を読んで止める。
  - かなで書いた番号（ゼロキュウゼロ…）
  - 一覧に無い SNS や連絡先の言い方
  - 名前・住所
- 報告の文の中の数字は、文の欄（感想 2 つと困り事の note）を全部合わせて 7 つ以上あると落ちる（番号を分けて書くのを止めるため）。寸法の数字の多い感想も落ちる。
- 連絡先の語（LINE・ライン など）の文字の間に空白や見えない文字を挟む書き方（L I N E yamada）は、式では止めない。空白を消して見ると、工作の普通の文（LINE is bent）まで落ちるため。止めるのは、受け入れ（`review accept`）の前に人が全文を読む所。
- 数の欄（仕上がりの点・止まった手順・かかった時間・困り事の手順の番号）の数字は、この合計に入れていない。入れると普通の報告も落ちる（点 4・手順 12・45 分・手順 3, 5, 12 で 9 つ）。それぞれの欄には上限があるが、番号を幾つもの数の欄に分けて運ぶ事は式では止めない。受け入れの前に人が全文を読む。
- JSON の報告の `params` は、雛形の範囲の中・小数 2 桁までの数だけを通す。ただ、範囲の中の整数を幾つもの欄に分けて番号を運ぶ事までは止めない（画面の入口は params を送らない）。

## 作り方の印（紙一枚・折るだけ・当時の材料）

形ごとに 3 つの印（#53）と、材料の前提を出す。どれも優劣の印ではなく、作り方の選択肢を選ぶ物と、考え直す所を見る物。

```bash
PYTHONPATH=src .venv/bin/python -m omochae.ways          # 一覧
PYTHONPATH=src .venv/bin/python -m omochae.ways --json   # サイトの絞り込みに使う
```

- 紙一枚: A4 1 枚に刷った紙だけで作れる。糊・はさみ・定規・カッターなどの道具は使ってよい（制作者の言葉「一枚の紙から作る選択肢もある」）。
- 折るだけ: 1 枚の紙を切らずに折るだけで作る（部品が 1 つで、切り込みも穴も糊代も無く、折り線が 1 本以上ある）。今の雛形には無い。
- 当時の材料: 紙のほかの材料が全部、江戸の頃にもあった物の語の一覧（竹・糸・紐・木・鈴・玉）に当たる時だけ付く（制作者の言葉「竹とか糸は江戸時代にもあったし使ったらよく再現できるということ」）。知らない物には付けない。今の物で代えた材料（油粘土・テープ・割ピン・ビーズ・厚紙など）は、一覧に出す。
- 材料の前提: 紙のほかの材料を、上の「設計の条件」の材料に当てて、3 つに分ける。落とす検査ではない。

  - 部品表に出る物（`bom`）と、用意する物の文に出る物（`prep`）を、別の一覧で出す。今のデータでは、作る途中だけ使う物（仮に留めるテープなど）と玩具に残る物を見分けられないため。

  - `--json` の各行の `premise`。`within` は、知っている語の中に金属・樹脂・一覧に無い物が無い時に true。文の一覧では、外の物を「材料の前提の外」に出す。

## 作った人の報告から型紙を直す

型紙は、組み上がった物の完成度と動きの完成度を高めるように直していく（制作者の方針・Issue #21）。材料は作った人の報告。
この repo は報告の形・検査・集計と、手元の入口と人の確認（下の omochae.intake。制作者の決定でエンジンの側・#22）を受け持つ。公開はサイト（提出物の側）が受け持つ。

```bash
PYTHONPATH=src .venv/bin/python -m omochae.feedback check examples/reports/spinner_pinwheel.json   # 0 通る / 3 落ちる
PYTHONPATH=src .venv/bin/python -m omochae.feedback summarize examples/reports           # 雛形・形ごとの集計（Markdown）
```

- 報告の欄:
  - `template`・`form`: 雛形と形
  - `built`: 組み上がったか
  - `moved`: `moved` 動いた・`partly` 少し・`not` 動かない
  - `finish`: 仕上がりの点 1〜5
  - `motion_notes`・`finish_notes`: 動きと仕上がりの感想
  - `problems`: 困り事の list。`kind`（cut・fold・glue・fit・motion・mark・material・finish・other、型紙の外は guide 案内・answer 聞く口の答え・site サイトの流れ）、`step`（手順の番号）、`note`
  - 作る様子（#23）: `stuck_step` 止まった手順・`gave_up` やめたか・`minutes` かかった時間（分）
- 名前・連絡先は書かない。決まりの外の欄と、文の中の数字の多い所（近くに 7 つ以上）・連絡先の語（@・メール・電話・LINE・SNS・URL）は落とす（F12.pii）。番号の書き方を式で追うとすり抜け続けたので、安全の側に倒した（寸法の数字も多いと落ちる）。式は補助で、受け入れの前に人が全文を読む。
- 式では名前や住所を拾えない。`summarize` は、人が全文を読んで受け入れた報告（`reviewed_at` がある）だけを数え、ほかはファイルの名だけ知らせる。
- `examples/reports/` は、この repo で追跡している作った見本の置き場。本物の報告は置かない（本物は git の外の `local/reports/`）。
- 集計の困り事のメモは信用しない文として扱う。1 行にして出し、Markdown では記号を無効にする（`--json` は 1 行にするだけ。使う側で JSON として読む）。
- 集計は、困り事が当たる行き先（寸法・床・組み方の文）を出すだけで、型紙も寸法も変えない。直しは人が採る。
- 集計の後半は、サービス全体の節（#23・制作者の決定「子どもの工作の様子を蓄積して、サービス全体の改善をする」）。止まった手順の多い所・やめた数・かかった時間・案内と聞く口とサイトの流れの困り事を、雛形をまたいで出す。

報告の入口（制作者の決定でエンジンの側に置く・Issue #22）:

```bash
PYTHONPATH=src .venv/bin/python -m omochae.intake serve                  # http://127.0.0.1:8765/ （手元の機械だけ）
PYTHONPATH=src .venv/bin/python -m omochae.intake review list            # 受付箱の ID
PYTHONPATH=src .venv/bin/python -m omochae.intake review accept <ID>     # 端末に全文を出し、人が読んで ID を打つと受け入れる
PYTHONPATH=src .venv/bin/python -m omochae.feedback summarize local/reports/accepted
```

- 受付箱と受け入れた物は local/reports/ に置く（git の外）。送った人の IP や端末の情報は残さない。写真は受け付けない。
- 却下（`review reject <ID>`）は中身を消し、ID と決まった理由の語だけを残す。

## 折れる様子を Origami Simulator で見る

型紙の折りのある部品を、[Origami Simulator](https://origamisimulator.org)（ブラウザーで折り線図を折って見せる道具）が読める SVG に書き出す。入口は型紙と同じ（`--scenario`、または `--template` と `--params`）で、書き出す前に型紙と同じ検査を通す（落ちれば 3）。

```bash
PYTHONPATH=src .venv/bin/python -m omochae.foldsim --scenario examples/fan_tab.json --out out/foldsim
# → out/foldsim/slider_fan_tube_foldsim.svg ・ _pusher_ ・ _base_ ・ _fan_（部品ごとに 1 つ）
```

書いた SVG を Origami Simulator の「File → Import」で開く。線の色は Origami Simulator の約束に合わせた（外形と中を切り抜く穴 黒 `#000000`・山折り 赤 `#ff0000`・谷折り 青 `#0000ff`）。検査に落ちた時と、書き出した時は、前の回の同じ頭の SVG を残さない（`--parts` で部品を減らした回は、その部品だけになる）。線の濃さは付けないので、どの折りも折り切った角度（180°）として扱われる。紙の厚みと摩擦は模擬しないので、実物の動きとは違う。部品を選ぶ時は `--parts fan,tube`。

## 3D の中で折って組んで確かめる（最小の 1 本）

型紙の部品を 3D の中で折って組み、刷る部品の形が組み方と合うかを確かめる。制作者の考え（2026-11-05「手順をAIが3Dで組み立てて、その過程を手順書にする」）の最初の 1 本で、制作者の決定により、提出の前は御来迎 つまみの形だけを見る。寸法の式でなく、刷る部品（外形・折り線・糊代・穴・溝の切り込み）から形を組むので、式と絵がずれた時に見つかる。

- `3D.close`: 外筒を、型紙の折り線で 90° ずつ折ると角筒に閉じる（糊代の折り線が、帯の反対の端の 1 面目の切る縁に合い、糊代が 1 面目に重なる）。内筒も同じく見る（竹串の線の前提なので）。糊代 1 つが折り線で区切られた 1 面である事も見る。折り線が面を 2 つに分けていない・長さ 0 の折り線・折り線でつながらない面・自分と交わる外形も、同じ床で落とす。
- `3D.face`: 見える面の部品（折り線を刷らず色の境で折る外筒）の色の面（刷った面）が、閉じた筒の外を向く。制作者の答え（2026-11-06。11-04 に作った時「色がついている所が外を向くよう折った」）で足した。凡例の谷折りは刷った面がへこむ向きなので、谷折りで刷っていた前の外筒は落ちる。隠れる部品（破線を刷る内筒）の向きは、組み立てに効かないので見ない。
- `3D.fan`: 押し上げて扇が口から出て開く所（最後の手順の後半。制作者の追加 2026-11-06）。台と扇は折らずに置く（台の上の面は内筒の上の端の高さ、扇は足の糊代の境の折り線が台に乗る高さ。扇の形は描いた部品から読む）。静かな時に畳んだ扇の上の端が口より下（隠れる）・押し上げ切ると要が口より上に出る・開く角の見込みの上限（帯の長さ÷板の高さ。実際は折り目で紙が立つので小さい）まで開いた扇（要のまわりの扇形）が外筒の横の面の口の縁に当たらない、を見る。静かな時の「口より下」は、口と同じ高さも落とす。軸の形で要の穴か足の折り線が無い扇も落とす。開く面は、外筒の開く糸の穴のある向かい合う 2 面に垂直な向きを型紙のデータから読む（今の型紙では 1 面目に平行。制作者が実物どおりと確かめた 2026-11-06）。穴があるのに向かい合う 2 面に無い型紙は落とし、穴が全く無い時だけ 1 面目に平行と置いて所見で言う。蛇腹の折りと開く仕組み（糸・紙のばね）は見ない。口の台の形の扇は、まだ置いていない。
- `3D.skewer`: 折った内筒が外筒の中に入り（断面のすき間が 0 より大きい）、内筒の 2 つの穴が向かい合い（高さも横もずれない）、穴を通す竹串が水平で、内筒を外筒の真ん中に入れて（穴のある 2 面目・4 面目を、外筒の溝のある 2 面目と 4 面目に向ける）、静かな時から押し上げ切るまで、竹串が外筒の溝の中を通る。

```bash
PYTHONPATH=src .venv/bin/python -m omochae.fold3d --scenario examples/fan_tab.json
# 閉じる 1 外筒（手順 3）: 型紙の折り線（山折り 4 本）を 90° ずつ折ると角筒に閉じる（継ぎ目のずれ 0.00mm・糊代は1 面目に 100% 重なる）
# 外向き 1 外筒（手順 3）: 色の面（刷った面）は 4 面とも筒の外を向く
# 閉じる 2 内筒（手順 5）: 型紙の折り線（谷折り 4 本）を 90° ずつ折ると角筒に閉じる（…）
# 通す 竹串（手順 6）: 2 つの穴は向かい合い（高さの差 0.00mm・横のずれ 0.00mm）、竹串は水平
# 入れる 2 内筒（手順 12）: 内筒は外筒の中に入る（断面のすき間 2.00mm）。…静かな時は竹串の中心が底から 7.5mm で、竹串（太さ 4mm）の端が溝から出る（…）
# 押し上げる 竹串（手順 13）: 竹串の中心は底から 7.5mm から 76.5mm まで 69mm 上がり、行程の全部で溝の中を通る（…押し上げ切ると溝の上の端に届いて止まる）
# 開く 4 扇（手順 13）: 静かな時、畳んだ扇の上の端は口より 2.0mm 下（隠れる）。押し上げ切ると、要が口より 21.0mm 上に出て、扇は 1 面目に平行に開き、開く角の見込みの上限（284°。…）まで開いても、横の面の口の縁に当たらない（縁までの余り 1.8mm）。…
```

手順の文は、3D で組む操作から作る（制作者の決定 2026-11-06。`omochae.ops3d`）。つまみの形の手順のうち、3D で組める部品の 5 本（外筒を角筒にする 3・内筒を角筒にする 5・竹串を通す 6・内筒を外筒に入れる 12・押し上げて蛇腹が開く 13）を、型紙のデータ（色の境か破線か・谷か山か・穴の数・部品の番号と名）から作る。13 の文は制作者の答え（2026-11-06）で「竹串の端を溝に沿って上に押し上げると、4 扇が 1 外筒の口から出て、蛇腹が開く」とし、押し上げる長さは文に入れない（長さは 3D の確かめの所見で言う）。折り方のデータを直すと、文も 3D も一緒に変わる。13 は組み立ての最後の動きとして足した（制作者の追加 2026-11-06。前の手順の番号はずらさない。口の台の形では 11）。ほかの手順と、ほかの押し方の形の手順は、雛形の文のまま。`omochae.fold3d` は、手順の文を作る操作の並び（`ops3d`）を、その順に 3D の中で行う（外筒を折る・内筒を折る・竹串を通す・入れる・押し上げる）。前の操作が落ちると、それに頼る後の操作は見ない。所見と落ちた行には、その操作の手順の番号を添える（上の例の「手順 3」など。番号は、雛形が手順の文と操作の種類を 1 つの並びで持つ `step_ops` から引く）。13 の「扇が口から出て開く」所は、台と扇を折らずに置いた形で `3D.fan` が見る。

入口は型紙と同じ（`--scenario`、または `--template` と `--params`）で、先に型紙と同じ検査を通す（落ちれば 3）。3D で落ちた時は `FAIL 3D.skewer [竹串] 押し上げ切る 5.0mm 手前で、竹串が外筒の紙に当たり、溝を通り切らない` のように、今の検査と同じ形の行で出す。終了は 0 通った / 3 落ちた / 4 確かめられない（型紙の検査に通る、つまみの形のほかの形と、ほかの雛形は、まだ組めないので 4）。`3D.close`・`3D.face`・`3D.skewer`・`3D.fan` は凍結の基準（criteria.md）の床（2026-11-05 と 11-06 の制作者の決定で足した。試験は `tests/test_fold3d.py`）。型紙の検査（`python -m omochae`）には繋いでいない（`python -m omochae.fold3d` だけが出す）。

### 作り方の 3D と、エンジンの 3D 組み立て検品

```sh
PYTHONPATH=src .venv/bin/python -m omochae.assembly3d --scenario examples/tora_v7.json --out out/3d/tora-v7.json --record out/3d/
```

作り方の 3D（手順と 1 対 1 の段ごとの形）を JSON で出す（サイトの組み立ての頁が読む。形の決めはサイトの担当と書き合わせた FORMAT-v1）。
出す前に、エンジンが組んだ形を自分で検品する（制作者の言葉 2026-11-07「エンジンは3D組み立て検品を自分でする（エンジンの性質として）」「組み立ての様子も作る」）。
全部の段の全部の姿・できあがりの動き・レシピが足す検品だけの姿（虎は静かな時の傾きから ±10° を 0.5° ずつ）で、紙の面がほかの面を刺さない・粘土の玉が紙に食い込まない・棒は穴の所でだけ紙を通る（3D.hit）、
机に置く形は机の下へ出ず（棒の端も）、静かな時に口の下に隠れる部品は口から出ない（3D.out）、組み終わりで決めた部品の刷った面の向き（3D.face）を見る。ほぼ平らな 2 面（貼る・重ねる所）は、両側へ 1mm 超出る時だけ刺すと見る。
落ちたら `FAIL 3D.hit [clayとbody] できあがりの動き（ほか 25 の姿）: 玉（半径 7.4mm）が胴の紙に 2.9mm 食い込む` のような行（同じ当たりは一番深い姿の 1 行）を出し、JSON を書かずに 3 で終わる（同じ置き場の前の JSON も消す）。
開く途中の扇のような近い形（custom）の部品の交わりは、所見（`NOTE`）として記録に残し、落ちにしない（硬い板の近い形では、要の所で紙が縮む形を表せない）。
`--record` を付けると、落ちても検品の記録（段ごとの終わりの姿の一覧 `<組>-check.png`・全部の姿の短い動画 `<組>-check.gif`・行 `<組>-check.txt`）を書く。落ちた所は赤、所見は橙。
入口は 3D の JSON を出す道だけで、型紙の検査（`python -m omochae`）にはつながない（決める側の決定 2026-11-07）。今の虎 v7・御来迎 v14 は通り、虎 v6 は落ちる（試験 `tests/test_check3d.py`）。
限り: 紙は折り線で分けた硬い面で、厚み・糊・たわみは入れない。姿と姿の間（頁が補う動きの途中）は、レシピが足す姿のほかは見ない。

検査は「刷れる・形の上で組める」事を見る物で、紙で動く事の保証や、昔の作り方の証明ではありません。面は硬い板、折り線は蝶番と見て、紙の厚み・たわみ・摩擦は入れていない。そのほかの前提と限り:
- 谷と山の向き（どちらの面が筒の外を向くか）は、見える面の外筒だけを `3D.face` で見る。隠れる部品の内筒は見ない（山に替えても、鏡に映した角筒として閉じて通る）。
- 外筒は折り線を刷らず、絵の色の境で折る。ここで折るのは型紙の折り線のデータで、色の境がその上にある事は見ない（型紙の絵は、折り線と同じ位置から面ごとに塗っている）。
- 内筒は外筒の真ん中に、穴のある 2 面目・4 面目を外筒の 2 面目・4 面目に向けて入れる（外筒は山折り・内筒は谷折りで鏡の向きに折れるので、1 面目と 3 面目は入れ替わって向かい合う）。すき間の分だけ横にずれる遊びは見ない。
- 竹串の太さは、溝の式と同じつまみの幅（`knob_width`）と見る。刷った穴の丸は、竹串の先であける所の印。
- 竹串の長さと端の位置は見ない（竹串は刷る部品でなく、型紙に長さが無い）。見るのは、竹串の線が溝を通るかだけ。

## エンジンごとの改善の輪（作る過程の記録 → 直しの案 → 人の採否 → 次の版）

型紙 1 枚の直し（寸法を 1 つ変えた次の版）とは別に、雛形から刷る全部の紙に効く直しを、作る過程の記録から起こす（Issue #63・#65・#68・#72・#79）。
機械は材料を束ねるだけで、採るかどうかも、直した後にどうなったかも決めない。
束を受けたら、人の操作を待たずに、直しの案と Issue の下書き（4 つの見出し）までを置き場に出す。材料は 2 つ: サイトからの束と、この repo の入口（`omochae.intake`）で人が受け入れた報告。人がするのは 4 つ: 束を渡す・下書きを読んで採否を決める・Issue を立てる・直しが入ったら版を刻む。この道具は、外へ何も送らない。

```sh
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop check examples/bundles/sample_made_up.json   # 束の形と連絡先の形（0 通る / 3 落ちる）
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop take examples/bundles/sample_made_up.json    # 入口。連絡先の形のある文は落として数だけ残す。続けて案を起こし、Issue の下書きを置く
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop list                     # 案の一覧（下書きが置き場にある案に印。show <番号> で当たった文つき）
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop propose                  # 案と下書きを起こし直す（take が続けて回すので、手で打つのは確かめたい時だけ）
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop adopt <案の番号> --by <人>   # 人が採る（reject で採らない）。番号は take と list が出す
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop release --commit <番号> --by <人> --sheet-set slider_fan=<組の名>   # 直しが main に入った後、次の版を刻む（--proposal EP-番号 を並べると、直しが入った案だけを版にする）
PYTHONPATH=src .venv/bin/python -m omochae.engine_loop compare                  # 版ごとの数を並べる（判定はしない）
```

- 束は、サイトの側が作る過程の記録（止まった所・動きの結果・工夫の言葉・感想・質問・話した事）を、雛形の id と刷った組ごとに束ねた JSON 1 つ。欄は決めた物だけで、決まりの外の欄がある束は束ごと断る。名前・連絡先・人の印の値・写真・声・映像・分より細かい時刻は入れない。
- 話した事は、声から字にした物を 3 つの種類で受ける（声そのものは束に無い）: `think` 作る前に仮説を見て話した考え・`craft` 作りながら話した工夫（手順の番号つき）・`keep` できた物を上げた後の話。群の `craft_steps` は、手順ごとの「話した工夫の数と人の数」。報告の欄の案（Issue #62）の `when` とは、idea が think・making が craft・made が keep に当たる。
- 受け入れた報告（`local/reports/accepted/`）も、`propose`（と `take`）が同じ道で集計する。受付箱（inbox）にあるだけの報告は、人が確かめる前なので数えない。報告 1 件は 1 人の 1 回の組み立てで、止まった手順・やめたか・困り事（種類・手順・文）・感想・かかった分・仕上がりの点（数の幅だけ）を写す。サービスの困り事（案内・聞く口・サイトの流れ）は、エンジンの案にしない。
- 作る前の型紙のレビュー（経験者が作らずに型紙を読んだ指摘）は、文の種類 `review` で受ける。人が確かめた字だけが束に来るので、1 件から「作る前のレビューの指摘を、雛形に入れるか見る」の案にする。作っていないので、止まった段にも工夫の数にも、報告の数にも入れない。
- 数と文は、紙（群の `paper`。報告では形の名）ごとに分けて数える。玩具は雛形と形で数えるため（制作者の決定 2026-11-05「型紙は玩具ごとに 1 枚」）。同じ雛形・同じ刷った組でも、紙が違えば別の玩具で、組み方の手順の数と番号も違う。案の鍵と題にも紙の名が入り、1 つの案に別の玩具の声が混ざらない。別の読みの形（`omochae.sheets`）の声も案にして、型紙でない事と型紙の形を「なぜか」に並べる（ヒントの声を入れるかは人が決める）。束の群の `paper` は無くてもよく、無い束は今までどおり読む。
- 案の行き先は 3 種。
  - 雛形: 同じ手順で止まった人が 2 人から（人の印の無い記録だけなら、止まったの札が 3 回から）。その段で話された工夫も、同じ案に付く。
  - 雛形: 止まったの札が重なっていない段でも、同じ手順で工夫を話した人が 2 人から（人の印の無い記録だけなら 3 件から）。
  - 雛形: 作った人の工夫の言葉（直した点・思いつき・話した工夫・できた後の話）は 1 件から。
  - 部品（雛形をまたぐ共有の所。刷り方・凡例・位置の印など）: 同じ種類の困り事が 2 つ以上の雛形で出た時。報告の困り事は種類（折り線・糊代・位置の印・切る線）を自分で持つので、その種類で束ねる。束の文は、語で拾う。
  - 生成の決まり（床と既定の寸法）: 検査を通って刷られた紙で、動かない側の札が 2 件から。「わからない」は動かない側に数えない。作る前の考えは、この案に付く（考えだけでは案にしない）。
- 束の上の段の `current_sets` は、雛形の id ごとの今の刷った組の名（無くてもよい。サイトの側が書く）。記録の紙の組が今の組と違う群から起きた案には、「今の組は ○○。この記録は前の組の紙の物（もう直っているかを、先に見る）」と並ぶ。前の組の記録だからといって、案を捨てはしない（直っていない事もある。決めるのは人）。`compare` では、今の組の行に印が付く。
- 案は数と当たった文だけを持ち、新しい寸法の値を持たない。採否は、人が名前を書いて決める。採った案は「次の版の予定」に入る。
- 採る時に `adopt --finding` で書く 1 行は、どういう知見で直すかを人が自分の言葉で書いた物で、台帳に入る（作った人の言葉をそのまま写さない。連絡先の形は断る）。版は雛形ごと（`--sheet-set 雛形=組`）にも、玩具 1 つ（`--sheet-set 雛形.形=組`）にも刻める。版が当たる玩具の出典も台帳に残る。サイトの作る側の頁が、この台帳を版の歩みとして読む。
- 共通化している知見（雛形をまたいで入れた直しの、どういう知見か）は、版に入った部品と生成の決まりの案から台帳に残る。輪を足す前に入った直しと、点検や制作者の確認から入った直しは、サイトの repo の版の表の文書に人が書く（2 か所に持たない）。
- Issue の下書きは、案が起きた時に置き場（`local/engine-loop/issues/`。git の外）に出る。採るのを待たない。頭に、今の状態（まだ採っていない案・採った案・版に刻んだ案）が出る。立てるのは人。
  - まだ決まっていない案は、束が増えて数や文が変わると、案と下書きが新しくなる（番号は同じ）。人が決めた案は、決めた時に見た数のまま書き換えない。
  - 採らないと決めた案の下書きは、置き場から消える（立てる物と間違えないため。案の記録は残る）。
- Issue の下書きは、作った人の言葉（当たった文）を、4 つの見出しの外の「手元の材料」に分けて置く。声から字にした話は、作る側だけが読む約束で残した言葉なので、Issue にはそのまま写さず、人が読んで自分の言葉でまとめる。
- 直しが main に入ったら、人が `release` で次の版を刻む。版の台帳は `data/engine/versions.json`（版の番号・採った案の番号と行き先と題・件数・commit・変わった刷った組）。作った人の文と、決めた人の名前は台帳に入れない。
- `compare` は、雛形ごとに刷った組ごとの数（報告の数・動きの札の数・止まった段の札と人の数・やめた段・最初に動くまでの分の幅・話した事の数）を並べる。上下や割合は出さない。件数が少ないと、差があっても偶然と分けられず、作った人も作り方も版ごとに違うため、読むのは人。
- 分かっている限り:
  - 見本の束 `examples/bundles/sample_made_up.json` は、形を見せるために作った見本で、実の記録ではない。実の記録の束は、サイトの試行の記録 2 件から出した物を通しただけ（群 1 つ・案 1 件。この案は前の組の紙の記録から起きた物で、中身は次の組でもう直っていた）。話した事の入った実の束は、まだ 1 つも通していない。採った案も、刻んだ次の版も、まだ無い（台帳は版 1 だけ）。
  - 話した工夫の案は、同じ段で話した人の数だけを見る。話の中身が同じ事を言っているかは見ない（人が読む）。手順の番号から直す所を引く表（雛形の `step_targets`）は、まだ使っていない。束が雛形の形（form）を持たず、表を持つ雛形も一部だけのため。
  - 名前は形では落とせない。束と案と Issue の下書きは git の外（local の下）にだけ置き、下書きは人が読んでから使う。
  - 文から困り事の種類を拾う所は、語の一致だけの荒い束ね。当たった文を案に付けるので、人が読んで確かめる。
  - 版の印は紙に刷らない（必須 2 種の刷った絵を変えないため）。版と紙は、束の「刷った組」と、`release` で書く刷った組でつなぐ。
  - 入口の床（F13.bundle・F13.pii・F13.proposal・F13.human・F13.version）は、この道具の床。凍結の基準の一覧には、まだ載せていない。
  - 束は、同じ出し元の物は新しい 1 つだけを数える（束はその時までの記録の全部なので）。
  - 受け入れた報告は、刷った組を持たない（紙に版の印を刷っていないため）。版ごとの数の並びでは「不明」の行に入る。同じ人が、サイトの記録と、この repo の入口の報告の両方に書いた時は、2 回数えられる（人を辿る印を持たないので、重なりは見分けられない）。
  - 採らないと決めた案は、後で数が増えても起こし直さない（別の案として起こす道は、まだ無い）。まだ決まっていない案が、新しい束で数の線を下回っても、案と下書きは置き場に残る（消すのは人）。

## セキュリティ

守っている事・していない事は、この repo の一番上の [SECURITY.md](../SECURITY.md) の「エンジン（engine/）」の節、見つけた時の知らせ方は同じ文書の終わりの節（点検 2026-11-07）。このエンジンは外の API を呼ばず、外へ何も送らない。外へ開く口は、手元の受付の画面（127.0.0.1）だけ。
穴を見つけたら、Issue や PR などのほかの人が読める所に書かず、repo の持ち主へ非公開で知らせる。

| exit | 意味 |
|---|---|
| 0 | 通る |
| 3 | 落ちる（どの検査が・どこで、を `FAIL <床> [<場所>] <理由>` で出す） |

## 置き場

- `src/omochae/` エンジン（`compose.py` 配置と検査の流れ・`floors.py` 描く前の検査・`marks.py` 印と刷った後の検査・`render.py` 描画・`textfit.py` 文字の幅・`fan_model.py` / `pivot_model.py` 扇と振り子の式・`metrics.py` 寸法から出る値）
- `src/omochae/templates/` 雛形
- `src/omochae/foldsim.py` Origami Simulator への書き出し
- `src/omochae/fold3d.py` 3D の中で折って組む確かめ（最小の 1 本: 御来迎 つまみの形の外筒の閉じと、溝と竹串）
- `src/omochae/assembly3d.py` 作り方の 3D（手順と 1 対 1 の段ごとの形）を JSON で出す。サイトの組み立ての頁が読む
- `src/omochae/check3d.py` 作り方の 3D の組み立て検品（3D.hit・3D.out・3D.face）と、検品の記録（段ごとの絵の一覧・短い動画）
- `src/omochae/ops3d.py` 3D で組む操作と、その操作から作る手順の文（御来迎 つまみの形）
- `src/omochae/sheets.py` 玩具 1 つに型紙 1 枚の表（どの形が型紙のたたき台で、どの形が別の読みか）
- `src/omochae/paper_words.py` 用意する物と部品表の紙の書き方。4 つ（コピー用紙くらいの厚さの紙・画用紙くらいの厚さの紙・画用紙より厚い紙・空き箱の厚紙）だけで、g/m²・mm の厚さ・「見込み」は書かない（制作者の指示 2026-11-05「ルールで徹底して」）。決まりに合わない書き方は `tests/test_paper_words.py` が落とす。必須 2 種の雛形は刷った絵を変えないため今の字のまま
  - 名前は計算に使う紙の重さか厚さから選ぶ（境は 110g/m²・0.12mm、220g/m²・0.25mm、0.5mm 以上は空き箱の厚紙）。計算は今までどおり数の値で行う。空き箱の厚紙の実物の厚さには幅があり（0.5〜1.5mm と見る）、その幅の中で登る板の噛みや車輪の芯が見込みどおり動くかは、実物で確かめていない。
- `src/omochae/engine_loop.py` エンジンごとの改善の輪（束の入口・直しの案・人の採否・次の版・版ごとの数の並び）
- `data/sources/` 出典の記録（国立国会図書館の書誌の値）
- `data/engine/` エンジンの版の台帳（`omochae.engine_loop`。数と行き先と、人が書いた知見の 1 行だけで、作った人の文は入れない）
- `tests/frozen/` 凍結した場面と合格の基準（照合の表 `manifest.json` と合わないと `./run.sh` は 4。凍結を変える時は理由を commit に書き、`.venv/bin/python tests/run_floors.py --write-manifest` で表も同じ commit で直す。落ちる場面は FAIL の行が 1 つか、期待の `lines` に全部の行の形を書く） / `tests/test_*.py` 式と検査の守りの試験
- `examples/` 最小の例
